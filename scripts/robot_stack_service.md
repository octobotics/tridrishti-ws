# Robot stack boot service

Build the robot packages before enabling the service. The generated unit uses
absolute paths to this checkout and runs the existing launcher as root, so the
launcher configures CAN and starts the nodes in its normal order.

The current `src/ouster-lidar-pub/config/config.json` may be set to the mock
sensor (`127.0.0.1`). Restore the real sensor address before installing for a
physical robot boot.

Preview the generated unit without changing systemd:

```bash
./scripts/install_robot_stack_service.sh --dry-run
```

Install and enable for the next boot:

```bash
sudo ./scripts/install_robot_stack_service.sh
```

To start immediately while installing, append `--start`. Otherwise, start it
later with `sudo systemctl start tridrishti-robot-stack.service`.

Check and control it:

```bash
systemctl status tridrishti-robot-stack.service
journalctl -u tridrishti-robot-stack.service -b -f
sudo systemctl stop tridrishti-robot-stack.service
sudo systemctl restart tridrishti-robot-stack.service
```

Node logs remain in `logs/robot/<session>/` and are created by root. The optional
`/etc/default/tridrishti-robot-stack` file can set launcher variables such as
`CAN_IFACE`, `CAN_BITRATE`, or `STARTUP_DELAY_SEC`.

To remove the service (stopping the running stack first):

```bash
sudo ./scripts/uninstall_robot_stack_service.sh
```

After moving this workspace, rerun the installer so the unit points to the new
path. The installer and uninstaller refuse to overwrite or remove a service
that was not generated by these scripts.
